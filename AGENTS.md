# Codebase Knowledge Graph (codebase-memory-mcp)

This project uses codebase-memory-mcp to maintain a knowledge graph of the codebase.
ALWAYS prefer MCP graph tools over grep/glob/file-search for code discovery.

## Priority Order
1. `search_graph` — find functions, classes, routes, variables by pattern
2. `trace_path` — trace who calls a function or what it calls
3. `get_code_snippet` — read specific function/class source code
4. `query_graph` — run Cypher queries for complex patterns
5. `get_architecture` — high-level project summary

## When to fall back to grep/glob
- Searching for string literals, error messages, config values
- Searching non-code files (Dockerfiles, shell scripts, configs)
- When MCP tools return insufficient results

## Examples
- Find a handler: `search_graph(name_pattern=".*OrderHandler.*")`
- Who calls it: `trace_path(function_name="OrderHandler", direction="inbound")`
- Read source: `get_code_snippet(qualified_name="pkg/orders.OrderHandler")`

* реальные интеграции;
* реальные сервисы.

Использование mock-данных допускается только при невозможности работы с реальной инфраструктурой.

## Hot Reload Production

Пользователь предпочитает подход:

**Hot Reload Production**

Идея заключается в том, что новые возможности сразу внедряются и тестируются в реальной рабочей среде лаборатории, а не в искусственно изолированных стендах.

Например:

не создавать mock API,

а подключить настоящее API.

Не писать тестовый OAuth,

а использовать настоящий OAuth.

Не имитировать LLM,

а подключить реальную модель.

Не эмулировать внешние сервисы,

если можно использовать настоящие.

# 13. Инструкции агенту

При работе агент должен придерживаться следующих правил:

1. **Думать системно**, рассматривая каждую задачу как часть общей архитектуры.

2. **Не предлагать mock-решения по умолчанию.** Если возможна безопасная интеграция с реальным сервисом, предпочтение следует отдавать ей.

3. **Проектировать решения промышленного уровня.** Даже экспериментальные компоненты должны быть готовы к последующей эксплуатации: конфигурация через переменные окружения, контейнеризация, логирование, мониторинг, обработка ошибок, безопасность и масштабируемость.

4. **Учитывать роль лаборатории.** Любые изменения должны естественно вписываться в ветку `development`, не нарушая ее назначения как исследовательской площадки.

5. **Предлагать решения, пригодные для переноса в продукт.** При разработке желательно учитывать возможность выборочного переноса компонентов в продуктовые ветки.

6. **Ориентироваться на повторное использование.** Новые модули следует проектировать так, чтобы они могли использоваться несколькими проектами экосистемы.

7. **Отделять факты от гипотез.** Особенно при обсуждении научных исследований и авторских теорий.

8. **Автоматизировать всё возможное.** При каждой задаче анализировать, можно ли заменить ручной процесс агентом, пайплайном или интеллектуальным сервисом.

9. **Учитывать исследовательский стиль работы пользователя.** Пользователь предпочитает быстро проверять гипотезы на реальной инфраструктуре, а затем доводить успешные решения до уровня продукта.

10. **Думать на несколько шагов вперед.** Помимо выполнения текущей задачи оценивать, как решение повлияет на развитие всей экосистемы в долгосрочной перспективе.

2. Приоритет источников информации:

* официальные инструкции репозитория и конфигурации (`config/`, `docker/`, `openspec/`);
* текущие контуры контейнеров и доступы инфраструктуры лаборатории;
* фактическое состояние работы сервисов и интеграций в рабочей среде.

3. Каналы инструментов:

* для анализа кода — по возможности MCP graph tools (`search_graph`, `trace_path`, `get_code_snippet`);
* для не-кодовых задач (конфигурации, документация, логи) — прямой просмотр файлов и логов с привязкой к текущему окружению.

4. Допуск ко всем изменениям:

* изменения в `development` допустимы как инженерные эксперименты;
* для продуктовых веток применяются только подтвержденные и отладочные через проверочный цикл решения.

5. Политика секретов и конфигурации:

* никогда не запрашивать и не выводить секретные значения;
* использовать плейсхолдеры и явные точки вставки в `.env`/`compose`;
* проверять окружение перед сборкой/перезапуском сервисов, где есть внешние ключи.
