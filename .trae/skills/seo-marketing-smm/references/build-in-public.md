# Build in public: ежедневная работа как контент-поток

Задача: показывать «разработку в новой реальности» — как команда, работающая в симбиозе с ИИ,
решает настоящие задачи. Источник тем — не фантазия маркетолога, а рабочий день: коммиты, инциденты,
замеры, отвергнутые гипотезы.

## Почему это работает

- В нише продают «автоматизацию» абстракциями; показ работы — единственное, что нельзя подделать.
- Технический покупатель (CTO) принимает решение по признакам инженерной честности: замеры,
  ограничения, описания провалов.
- Материал уже произведён — он лежит в репозитории и в переписке; остаётся оформить.
- Это же питает найм: сильные инженеры идут туда, где видно, как думают.

## Конвейер: от задачи к публикации

```
День работы → журнал наблюдений → тема недели → артефакт → нарезка по каналам
```

1. **Журнал наблюдений.** Раз в день одна строка: что сломалось, что удивило, что измерили, что
   отвергли. Держать в репозитории (`docs/journal.md` или заметки) — иначе через неделю не вспомнить.
2. **Тема недели.** Из журнала выбрать одно наблюдение, у которого есть *механизм* и *цифра*.
3. **Артефакт.** Пост, разбор или статья — в зависимости от глубины (см. форматы ниже).
4. **Нарезка.** Цепочка публикаций по каналам (`channels.md`).

Правило отбора: тема годится, если её можно закончить фразой «поэтому теперь мы делаем так —
и вот что это дало». Без вывода это дневник, а не контент.

## Где брать темы

Проверенные источники внутри своих же репозиториев:

```bash
# что делали за неделю — готовый список поводов
git -C /root/xteam-pro-site log --since='7 days ago' --pretty='%h %s'
git -C /root/StudyNinja-Eco log --since='7 days ago' --pretty='%h %s'

# самые переписываемые файлы = места, где болело
git log --since='3 months ago' --name-only --pretty=format: | sort | uniq -c | sort -rn | head -20

# коммиты с признаками боя
git log --grep='fix\|revert\|perf\|hotfix' --since='1 month ago' --pretty='%h %ad %s' --date=short
```

Ещё источники: инциденты и их разбор, замеры производительности до/после, отвергнутые архитектурные
варианты (ADR), баги с неочевидной причиной, эксперименты с моделями и промптами, ограничения
инструментов, найденные на практике, обновления собственных библиотек, вопросы клиентов, которые
повторяются.

Особая ценность — **revert-коммиты и отменённые решения**: «мы сделали, показали, забраковали» —
это честность, которой в нише нет.

## Восемь форматов, которые всегда есть

| Формат | Из чего рождается | Куда |
|---|---|---|
| Разбор инцидента | падение, странный баг | Telegram → Habr, если глубоко |
| «До и после» с числами | оптимизация, профилирование | Telegram, VC, LinkedIn |
| Отвергнутая гипотеза | эксперимент, который не взлетел | Telegram, Habr |
| Инженерное решение недели | архитектурный выбор | Habr, dev.to |
| Инструментальная заметка | новая утилита, скрипт, приём | Telegram, X |
| Как мы работаем с ИИ | агенты, промпты, ревью моделью | VC, LinkedIn, Telegram |
| Демонстрация | UI, визуализация, граф, дашборд | видео: YouTube/RuTube/клипы |
| Итог месяца | журнал наблюдений целиком | рассылка, Дзен |

## Фильтр безопасности

Перед публикацией любого материала из рабочего процесса проверить:

- [ ] Нет секретов: ключей, токенов, паролей, `.env`, внутренних доменов и IP, схем сети
- [ ] Нет данных клиента: имён, объёмов, условий договора; обезличено там, где действует NDA
- [ ] Нет персональных данных пользователей ни в скриншотах, ни в логах, ни в примерах
- [ ] Нет описания незакрытой уязвимости своей или чужой системы
- [ ] Скриншоты просмотрены попиксельно: вкладки браузера, пути, почта, токены в URL
- [ ] Утверждения о партнёрах и клиентах согласованы с ними
- [ ] Цифры — настоящие и воспроизводимые; методика замера указана

Сомнение трактуется в пользу неразглашения: сильных тем всегда больше, чем времени на них.

## Шаблоны постов

**Разбор инцидента (Telegram, 1 500–2 500 знаков):**
```
Симптом (одна строка, конкретно: что видел пользователь)
Первая гипотеза и почему она оказалась ложной
Что показало измерение
Настоящая причина — механизм, а не название
Что изменили (диф в двух строках или команда)
Что забрали в практику
```

**«До и после» (любой канал):**
```
Задача и почему медленно/дорого/ненадёжно
Что мерили и чем
Число до → число после, условия замера одинаковые
За счёт чего именно (одно предложение)
Где это не сработает
```

**Отвергнутая гипотеза:**
```
Что казалось хорошей идеей
Как проверяли
Почему отказались (цифры или конкретный эффект)
Что делаем вместо
```

**Технический лонгрид (Habr):** см. `content-playbook.md`, раздел «Экспертный лонгрид».

## Как не выгореть

- Планка «интересно» — не «идеально»: пост из трёх абзацев с одной цифрой полезнее ненаписанной статьи.
- Одна большая тема в месяц, остальное — короткие формы из журнала.
- Писать сразу после события, пока помнятся детали; публиковать — по расписанию.
- Держать запас из 3–5 черновиков: он снимает панику дедлайна и позволяет выбирать по настроению.
- Не превращать канал в отчёт: читателю нужен вывод, применимый к его работе, а не летопись команды.
