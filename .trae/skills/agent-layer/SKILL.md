# Слой агентов

## 1. Что это

На этом хосте одну и ту же экосистему ведут несколько агентов трёх вендоров:
Claude Code, Codex и Trae. Раньше каждый знал только свой каталог и свой набор
инструкций, поэтому одна и та же находка исследовалась трижды, а решение,
принятое в одной сессии, не доживало до следующей.

Слой убирает именно это. Он даёт один реестр, один канонический стор скиллов и
один способ передать работу. Вендор становится деталью исполнения: `Codex`,
`Claude` и `Trae` -- разные исполнители одной роли, а не разные роли.

Реестр и инструмент: `/root/.agents/`, команда `xt-agents`.

## 2. Первое, что делает агент

```bash
xt-agents whoami     # кто я в этом каталоге, чем владею, кто рядом
xt-agents inbox      # что мне передали другие агенты
```

`whoami` выводит идентификатор вида `<проект>@<вендор>` — например
`studyninja-api@codex`. Этот идентификатор адресуемый: под ним агента находят
остальные.

Если каталог не принадлежит ни одному проекту реестра, это не ошибка среды, а
пробел реестра: проект добавляется в `/root/.agents/registry/projects.yaml`.

## 3. Откуда берутся скиллы

Канон один: `/root/.agents/skills/`. Второй копии не существует, и это
проверяемо.

| Вендор | Как получает | Проверено |
|---|---|---|
| Codex | читает канон нативно как отдельный skill root | `codex debug prompt-input` показывает корень `/root/.agents/skills` |
| Claude Code | симлинки `~/.claude/skills/<name>` в канон | новый симлинк подхватывается живой сессией |
| Trae | физические копии в `<проект>/.trae/skills` | у Trae нет пользовательского стора |

Набор каждого агента складывается из двух частей:

- **общий знаменатель** — уровни `core`, `infra`, `method`: политики поведения,
  инфраструктурная экспертиза `/root`, компиляция знаний. Одинаков у всех;
- **уникальный набор проекта** — объявлен в `projects.yaml` у конкретного
  проекта: продуктовая, архитектурная, дизайнерская или маркетинговая
  экспертиза именно этой области.

Проект не заводит своей копии инфраструктурного знания. Если ему нужен скилл,
которого нет, скилл добавляется в канон и объявляется в реестре, а не
копируется в проект.

## 4. Три канала и правило выбора

Правило одно: **чем дольше решение должно прожить, тем правее канал**.

| Канал | Живёт | Для чего | Команды |
|---|---|---|---|
| Шина | до переустановки хоста | живой обмен между сессиями | `xt-agents send` / `inbox` / `ack` |
| Граф | между сессиями и вендорами | структурное знание о коде, ADR-решения | инструменты `codebase-memory-mcp` |
| GitHub | постоянно, виден людям | обязательства и приёмка | `gh`, доска XTeam Control Plane |

Следствия, которые чаще всего нарушают:

- Шина **не источник правды**. Решение, прожившее дольше сессии, переносится в
  граф или в GitHub. Иначе оно исчезнет вместе с шиной.
- Проект, которого нет в графе, индексируется **до** работы. Иначе следующий
  агент повторит тот же поиск с нуля.
- Решение, влияющее на чужой проект, пишется в ADR **этого** проекта, а не
  только в свой отчёт.
- Секреты не попадают ни в один канал. Шину читает любой агент на хосте.

## 5. Передача работы

Формат один для всех вендоров, чтобы принимающий не разбирал чужие соглашения:

```bash
xt-agents handoff --to studyninja-uikit@claude-code \
  --intent "Починить обрыв прогресс-бара после смены цели" \
  --state "Воспроизведено на dev, причина в кеше React Query" \
  --evidence "make check ок; curl /api/v1/goals — 200, поле stale" \
  --next "Инвалидировать ключ goals при смене цели" \
  --issue 412
```

Что происходит: блок печатается, кладётся в шину адресату и, если указан
`--issue`, дублируется комментарием в GitHub.

Обязательные поля блока: `from`, `to`, `project`, `intent`, `state`,
`evidence`, `blocked_by`, `reversible`, `next`. Пустое `evidence` -- это не
передача, а перекладывание: принимающий начнёт с проверки того, что уже было
проверено.

`--to open` означает «любому, кто возьмёт»: блок печатается и идёт в issue, но
не адресуется конкретному агенту.

`--irreversible` помечает передачу, где следующий шаг необратим. Принимающий
обязан получить подтверждение владельца **до** действия, а не после.

## 6. Границы полномочий

| Уровень | Что можно |
|---|---|
| `observe` | читать и отчитываться фактами |
| `build` | менять код в рабочей ветке, открывать PR |
| `operate` | плюс управлять лабораторным стендом |
| `release` | плюс инициировать релизные шаги |

Поверх уровня действуют правила, которые не отменяются ничем:

- архивные репозитории полностью исключены из поиска, анализа, упоминаний и
  GitHub-операций без явного указания владельца на конкретный репозиторий и
  действие (скилл `no-archived-repositories`);
- реальные production-данные, персональные данные, телеметрия и обученные на
  них веса никогда не переносятся в публичные репозитории, Lab, Dev или hot-dev
  (скилл `no-production-data-publication`);
- целевое состояние активных репозиториев -- публичная двойная лицензия
  AGPL-3.0-only + commercial за исключением явного private allowlist; изменение
  видимости разрешает только пройденный publication/IP/data/rights gate
  (скилл `public-repository-policy`);
- прямой push в защищённые ветки запрещён; единственное исключение --
  single-writer coordinator обновляет `hot-dev` под identity `AndrewHakmi` без PR и
  GitHub checks, но без force-push/delete (скилл `hot-development-lane`);
- необратимое действие требует подтверждения владельца;
- дефект живой среды сначала получает запись, потом правку;
- работа не подписывается ИИ-авторством (скилл `no-coauthor`);
- планы описываются фазами и критериями, а не сроками
  (скилл `no-human-time-estimates`).

Всё, что касается Production и доступов, остаётся за скиллом
`production-access`; архитектурные решения о лаборатории -- за
`xteam-control-center`; путь от находки до PR -- за `lab-to-pr`.

## 7. Изменение самого слоя

Слой описан данными, а не кодом. Правится реестр, затем раскатывается:

```bash
xt-agents inventory              # что фактически есть на диске
xt-agents sync --dry-run         # что изменится
xt-agents sync                   # раскатать
xt-agents doctor                 # топология + YAML/spec каждого SKILL.md
xt-agents check                  # фейлится при расхождении или невалидном skill
```

Файлы реестра:

- `registry/vendors.yaml` — как каждый вендор находит скиллы; поля помечены
  FACT только если проверены на этом хосте;
- `registry/skills.yaml` — каталог и уровни раздачи;
- `registry/projects.yaml` — проекты и их уникальные наборы;
- `registry/agents.yaml` — глобальные роли и уровни полномочий;
- `registry/channels.yaml` — каналы и схема передачи.

`doctor` проверяет не только registry/hash/topology, но и каждый канонический и
Trae-проектный `SKILL.md`: YAML frontmatter, разрешённые поля, обязательные
`name`/`description`, kebab-case и совпадение имени с каталогом, типы metadata и
наличие инструкций. Для Trae symlink считается ошибкой, потому что его адаптеры
должны быть физическими копиями. Размер свыше 500 строк — предупреждение по
рекомендации Agent Skills, а не блокирующая ошибка.

Ручная правка сгенерированных `<проект>/.agents/CONTEXT.md` бессмысленна:
следующий `sync` их перезапишет. Менять надо реестр.

## 8. Чего слой не делает

Он не оркестратор: не запускает агентов, не раздаёт задачи и не решает за
владельца. Он делает агентов взаимно видимыми и даёт им общий язык.

Он не может быть несущим для продакшена. Если выключить `/root/.agents`,
проекты, CI и продакшен продолжают работать — теряется только взаимная
осведомлённость агентов. Это то же правило автономии, что и у Control Center:
`Lab → Prod` разрешено, `Prod → Lab` запрещено.
